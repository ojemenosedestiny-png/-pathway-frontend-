2. USER JOURNEY AND ACCOUNT STATES
=====================================================
1. Visitor signs up for a FREE applicant account (email + password, email
   verification, rate limiting). Applicant number: APP-2026-0001.
2. Applicant completes the application form (section 4) and pays the
   application fee (section 5). Until the application fee is VERIFIED:
   no hostel booking, no exam payment, no consultation booking.
3. When Finance verifies the application fee: account becomes a Student,
   a Student ID is generated (PU-2026-000123 style, atomic, unique,
   never reused) and the student is emailed. Login accepts email or
   Student ID.
4. Inside the portal the student chooses exams (WAEC, NECO, Cambridge
   International, BECE, SAT, HMB, others from the catalog). Each exam
   creates its own invoice from the admin fee table.
5. Hostel is booked from the portal after the application fee is verified
   (section 6).
Parents or guardians can be the payer; record guardian consent for
applicants under 18.

5. PAYMENTS (bank transfer + proof, invoice-based)
=====================================================
Student side: every charge is an invoice (application fee, each exam,
hostel). Pay screen shows the amount due, the ACTIVE school account for
that purpose (copy buttons), and a unique reference to use as the transfer
narration. Student uploads proof (JPG/PNG/PDF, 5 MB) with payer name,
amount, bank, date, transaction reference. Statuses: Awaiting proof, Under
review, Verified, Rejected (with reason, re-upload allowed). Proofs are
private, never public.

Admin side (Finance): Payment accounts manager. Editing or adding an
account requires password + 2FA re-confirmation, is audit-logged (masked
old/new), shows "last changed by", emails the Super Admin, and snapshots
the account on each payment. Verification queue: proof viewer with zoom,
expected vs claimed amount, application details; actions Verify, Reject
with reason, Request clarification. Reminder text: "Confirm the credit in
the bank account before verifying." Auto-flag reused images (hash), wrong
amounts, reused references. On Verify: invoice paid, PDF receipt emailed,
tracker updated, Student ID created if first verified payment, live event
sent to the student. CSV export. Keep an interface so Paystack/Flutterwave
can be added later.

EXAMS AND TIMETABLE (core feature)
- Student sees only their enrolled exams. Views: calendar and list, with a
  countdown to the next paper.
- Each entry: exam body, subject/paper, date, start time, reporting time,
  duration, venue or centre, candidate instructions, and status (Published,
  Rescheduled, Cancelled).
- Times stored in UTC and shown in Africa/Lagos (WAT) with a timezone label
  and an option for the student's local time.
- Changed entries show an "Updated" badge and a "What changed" panel (old
  vs new, reason, who, when), from the TimetableChange log.
- Add to calendar (.ics download and a private subscribe link), print or
  PDF timetable, and an admission/exam slip generated only when the exam
  invoice is verified and the Exams Officer approves.
- Admin (Exams Officer): create and edit entries by exam and session, CSV
  bulk import, draft/publish, preview as student, clash detection for
  students enrolled in overlapping papers, and notify only affected
  students when published or changed. Changes after publishing require a
  reason, which students see.

=====================================================
8. LIVE UPDATES (REAL TIME)
=====================================================
Goal: when an admin changes something, the affected student's open portal
updates within about 2 seconds with no page refresh.
- Use Server-Sent Events (GET /api/events, authenticated, text/event-stream)
  with a heartbeat every 25 seconds. Support Last-Event-ID so missed events
  are replayed after a reconnect. Auto-reconnect with exponential backoff.
  Fall back to polling every 30 seconds if SSE is unavailable.
- Fan out across server instances with Redis pub/sub (or Postgres
  LISTEN/NOTIFY), and write each event to RealtimeEvent for replay.
- Each user receives only their own events and announcements targeted to
  them. Admins receive admin events (new application, new proof, new
  hostel booking). Never send another student's data.
- Event types: timetable.published, timetable.changed, timetable.cancelled,
  payment.status_changed, invoice.created, application.status_changed,
  document.status_changed, hostel.booking_changed, result.published,
  announcement.published, message.received, student.id_issued.
- Client: a small store that applies events to the relevant screen, shows
  a toast ("Your WAEC Mathematics paper has been rescheduled"), updates
  the notification bell, adds "Updated" badges, and never loses unsaved
  form input.
- Build a Live indicator in the portal footer (Connected / Reconnecting)
  and an admin "Realtime health" page.
- Proxies and hosts must not buffer the stream: set Cache-Control:
  no-cache, X-Accel-Buffering: no, and disable compression for the
  event route.
